In plain language

How a broadcast becomes data you can trust

No jargon, no computer-vision vocabulary. If any of this is unclear, that is a bug in the writing — the product is meant to be usable without reading it at all.

The six steps

All six steps are the machine, and it runs unattended: a broadcast that airs is found, read and published without anyone starting it. A person comes after publication, not before it — every reading is published beside the frame it came from, and anyone can audit it and correct what is wrong. That is a deliberate trade: the alternative is a queue that only moves when someone is available, and a site that goes stale whenever nobody is.

What “published” means here

A published line-up has all four of these

  • Five heroes read off the actual broadcast frame, not entered by hand from memory.
  • A confidence the detector was willing to stand behind. A slot it could not read is recorded as unknown — it is never guessed, and a line-up with an unknown slot is not a line-up.
  • The image file it was read from, kept and linked.
  • The tier it earned, stated on the page: confirmed (a person checked it), strong (hundreds of frames agreed), or provisional (accepted, but on weaker evidence — worth auditing first). A reading judged wrong is marked rejected and is never published.

Where the facts come from

Two separate sources that never mix:

  • Hero compositions only ever come from reading the video, or from a person correcting that reading. FACEIT can never supply a composition.
  • Match facts — teams, maps, scores, bans — come from FACEIT, official pages, or manual entry.

Keeping them apart is why a score being wrong can never make a composition wrong, and vice versa. A third, imported source — a community spreadsheet — is explained below; it never becomes a VOD reading either.

Two kinds of record: VOD timelines and spreadsheet observations

VOD verified

The tracker watched the broadcast and read every hero portrait on the HUD, second by second. It knows when each hero was on the field and for how long, when a player swapped, and it keeps the frames it read as evidence.

  • Time on a hero counts only live play — the round windows — never setup, replays or the gaps between rounds.
  • A moment where a portrait could not be read is unknown. It is reported, and it is left out of every percentage: a share is “seconds on this hero ÷ seconds we actually know”, and the coverage beside it tells you how much of the map that is.
  • Swaps are only counted when hundreds of frames agree; rejected ones are shown as rejected.

Spreadsheet imported

A public, community-maintained Google Sheet documents OWCS series by hand: map picks, map results, hero bans and the heroes listed for each player. It covers far more matches than the tracker has read, and we import all of it — every tab.

  • It records what was played, not when or for how long. A player listed on “Juno / Lúcio” played both at some point; the sheet does not say which first or for how long, and nothing on this site pretends it does.
  • So spreadsheet numbers are counts — appearances, appearance rates, bans, picks — labelled “Spreadsheet observation”, and never called time-weighted.
  • Values the importer cannot recognise (a typo’d hero, an unknown team) are kept with their original text and never guessed.

When both sources describe the same map

The pipeline links a spreadsheet map to a VOD map only when it is safe to (same two teams, matching date, map and map number — ambiguous cases wait for a person). Both records are kept, and every field is compared:

Both sources agree Partly matched Conflicting sources

“Partly matched” means nothing disagrees but some field is recorded by only one source. “Conflicting” means they disagree — both claims are shown and the site never picks one; a map whose winner is disputed is left out of every win count. Win shares everywhere are observational (“observed map-win share”, “usage among eventual map winners”): they describe what happened, not what causes wins.

What happens when the machine is wrong

It gets corrected, and the original reading is kept.

A correction never deletes what the detector saw. It is recorded as an additional, attributed, reversible layer: the hero it read, the confidence it had, the frame it read from, who overruled it, when, and why. Both sit side by side in the record, and the correction file is committed to git — so the history of every change is public and permanent.

This is deliberate. A tracker that quietly overwrites its own mistakes cannot be audited, and a tracker that cannot be audited is just an opinion.

Because publication no longer waits on a person, the audit is the real safeguard rather than a formality — so it is open on the published site itself, not behind an operator's tool. Anything you can read, you can check against the frame it came from.

What this site does not claim

Running your own copy

The published site is a static file. It has no server, so it cannot download a video — which is why submitting a game here hands you a command instead of pretending to work.

To actually process a broadcast you run the tracker on your own machine. It is free and open, and it does not phone anything home.

  1. Install Python 3.11 or newer, plus ffmpeg and yt-dlp.
  2. Clone the repository and run pip install -r requirements.txt.
  3. Start the local portal: 
    python3 pipeline/serve.py
  4. Open the address it prints. Every page you have seen here works the same way, except now Submit really submits and Review really writes.
