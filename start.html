This page turns a day of OWCS broadcasts into verified hero compositions. You install four free tools once, then every match day you run one command, paste the links, and leave it alone. It will stop and ask you a few questions — those questions are listed below with exactly what to click.

Do you actually need this page?

Only if you want to add matches. If you just want to read what teams played, everything published is already on the front page — no setup, no install, nothing to run.

1 · Install the four tools (once, ~15 minutes)

All four are free and none of them need an account, an API key or a login. Everything below is for Windows; on macOS or Linux the same four tools install from brew or your package manager.

1a

Python

Get it from python.org/downloads. In the installer, tick “Add python.exe to PATH” on the first screen — if you miss that box nothing else will work.

python --version

Should print 3.10 or higher.

1b

ffmpeg — reads the video

Download a Windows build from gyan.dev/ffmpeg/builds, unzip it to C:\ffmpeg, then add C:\ffmpeg\bin to PATH (Settings → System → About → Advanced system settings → Environment Variables → Path → New). Close the terminal and open a new one, then check:

ffmpeg -version
1c

yt-dlp — downloads the broadcast

Grab yt-dlp.exe from the releases page and drop it into C:\ffmpeg\bin — that folder is already on PATH from the last step, so there is nothing else to change.

yt-dlp --version
1d

Deno — the part everyone forgets

YouTube scrambles its video links and yt-dlp needs a JavaScript runtime to unscramble them. Without one, downloads start and then sit at zero bytes forever. Install Deno (one command, no account) and this whole class of problem disappears.

deno --version

Node.js works too — the pipeline detects either.

1e

The project's Python packages

In the folder you downloaded this project into:

pip install -r requirements.txt
Check everything at once

The launcher in step 2 runs this for you, but you can run it yourself any time. It lists every tool with OK / WARN / FAIL and the exact fix for each one.

python pipeline/preflight.py

2 · Every match day: double-click one file

Windows: double-click start.bat

In the project folder. It checks your tools, tells you plainly if anything is missing, starts the control room, and opens the portal in your browser by itself. On macOS or Linux, double-click start.command (or run ./start.command) instead.

A black window will open and stay open. Leave it open — it is the program. Closing it stops everything (nothing is lost; work resumes next time).

If you'd rather type it yourself, that's the same thing:

python pipeline/serve.py

Either way you land on http://localhost:8000/portal.html. The paste box should say “control room detected”, with a row of green pills under it confirming ffmpeg, yt-dlp and the JS runtime are all present. A red pill there names exactly what to install and the command to do it. If the box says “static hosting” instead, the launcher isn't running, or it's running in a different folder.

3 · Paste the whole day at once

Go to the OWCS channel, open each VOD you want, and copy its link. Paste all of them into the box together — one per line, or separated by spaces or commas. Anything that isn't a link is ignored, so you can paste straight from a schedule or a chat message.

https://www.youtube.com/watch?v=aaaaaaaaaaa https://www.youtube.com/watch?v=bbbbbbbbbbb https://www.youtube.com/watch?v=ccccccccccc

Press Convert broadcast. The first link starts immediately; the rest join a queue shown underneath and start on their own as each one finishes. You do not have to come back between broadcasts.

You can also skip the copying entirely: the Auto match finder section below the paste box lists every broadcast it found on the official OWCS channels, and Ingest sends one into exactly the same queue.

How long does one broadcast take?

Roughly 30–90 minutes of unattended work for a full match day VOD: most of it is downloading several gigabytes, then about 15–40 min making a small scanning copy, then a few minutes finding the maps. The log shows a live percentage and an ETA for every stage — if a line says eta 0:18:00, that is a real estimate, not a spinner.

The computer has to stay awake and the terminal window has to stay open. Closing the lid pauses everything; nothing is lost, but nothing progresses either. A stopped download resumes where it left off when you start it again.

4 · The questions it will ask you

The pipeline runs every step it can decide on its own, and deliberately stops at the ones where being confidently wrong would be worse than being slow. Each stop shows up as a card on the portal with buttons. This is the complete list — there are no others.

“Is this really an OWCS broadcast?”

It found a video on a channel it hasn't been told to trust.

You: type your name in the name box, then click Approve source if it's a real OWCS broadcast, or Reject source if you pasted the wrong link. Your name is recorded with the decision.

“I worked out where the HUD is — does this look right?”

Every broadcast puts the hero portraits in slightly different places, so the first time it sees a new broadcast style it measures the layout itself and asks you to confirm it rather than guessing.

You: click Approve layout. If it refused to calibrate at all, it says why — that usually means the broadcast has an unusual overlay, and the honest answer is to skip that VOD.

“Here are the maps I found — which ones are real?”

It scans the whole broadcast and proposes the stretches that look like live gameplay, with thumbnails and how many gameplay frames it saw in each. Desk segments, replays and scoreboards are already thrown out.

You: look at the thumbnails. Approve the ones that are real maps, reject the ones that aren't. The tick-box above the paste box (“auto-accept clean identity proposals”) lets it accept the unambiguous ones by itself — anything uncertain still waits for you.

“Here's what I read — publish it?”

The final gate. Nothing reaches the public site until you press this.

You: Detect (dry run) to see the reads, Commit detection to save them, then PUBLISH.

5 · Publishing

Publishing writes the approved compositions into the site's data file. Refresh the front page and the new maps are there, with their evidence — and every hero you just added shows up on the hero board, with the sample size it came from. If you have the project connected to GitHub, committing and pushing that data file is what makes it appear on the live site.

What gets published is only what cleared review. A map where the detector wasn't sure is held back rather than shown with an asterisk — the reasoning behind that is on How it works.

When something breaks

Every failure the pipeline knows about is printed with a code and a remedy, and nothing is lost when one happens — jobs resume, downloads continue from where they stopped, and you can hit Retry on the card. These are the ones you'll actually meet:

youtube_js_runtime_missing — or a download stuck at 0 bytes

yt-dlp can't unscramble YouTube's video links.

Fix: install Deno (step 1d), then hit Retry.

youtube_media_forbidden / youtube_bot_check

YouTube refused this particular download attempt. The pipeline already retries with five different strategies before showing you this.

Fix: wait a few minutes and hit Retry. If it keeps happening, the advanced panel at the bottom of the portal explains how to point it at your browser's cookies.

ffmpeg_crashed

ffmpeg died while reading the video. The pipeline now recovers from this by itself — it re-reads the affected stretch one frame at a time — so you only see this code if the file on disk is genuinely unreadable.

Fix: delete that broadcast's downloaded file and hit Retry to download it fresh. If it fails again, update ffmpeg.

“no download progress for 300s — killed”

Something stopped moving entirely and was shut down on purpose rather than left to hang forever.

Fix: hit Retry. Downloads resume, so a stall costs minutes, not the whole broadcast.

insufficient disk space

A full match-day VOD is several gigabytes and it checks before downloading, not after.

Fix: clear space, or delete finished broadcasts from data/worker/jobs/. Published results don't need the video kept.

Nothing is happening and there's no error

Check the terminal window is still open, and look at the live log under the paste box — every stage prints a heartbeat with elapsed time, so a genuinely silent job is unusual.

Fix: Cancel stops the current job and clears the queue behind it. Nothing already downloaded is thrown away.

Honest answers

  • Does it cost anything? No. No API keys, no subscriptions, no paid services — the whole thing runs on your own machine against public video.
  • Can it do a full day without me? The downloading, scanning and map-finding, yes — that's most of the wall-clock time. The four questions above still need a person, by design. Queue everything in the morning, answer the questions when you get back.
  • Will it ever make something up? No. Anything it isn't sure about is withheld rather than guessed, which is why a broadcast sometimes produces fewer maps than you expected.
  • I broke something — can I start over? Yes. Deleting a job's folder under data/worker/jobs/ and pasting the link again starts that broadcast from scratch. Nothing published is affected.
  • Where do I look when I'm stuck? The live log under the paste box is the whole truth — every command it runs, every failure and every remedy is printed there.
